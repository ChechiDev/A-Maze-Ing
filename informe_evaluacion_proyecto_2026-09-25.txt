1. LO QUE ESTA BIEN (verificado)
==================================================================
- Estructura del codigo (mazegen/ vs ui/ separados, arquitectura
  limpia: grid, generator, modes/, strategies/, encoder, solver,
  validation, pattern42).
- Entry point exacto: python3 a_maze_ing.py config.txt
- Config file: WIDTH, HEIGHT, ENTRY, EXIT, OUTPUT_FILE, PERFECT
  + SEED opcional. Comentarios con #, config.txt por defecto en
  el repo.
- Codificacion hexadecimal de paredes correcta (bit N=1, E=2,
  S=4, W=8), verificada contra la tabla del subject.
- Formato del archivo de salida (grid, linea vacia, entry, exit,
  path) coincide exactamente con el ejemplo del PDF.
- Coherencia de paredes compartidas garantizada estructuralmente
  (Grid.open_wall abre siempre ambos lados a la vez).

  devuelve vecinos dentro de limites).
- Prohibicion de areas abiertas 3x3 implementada
  (has_open_3x3_area / has_playable_open_3x3_area) - requisito
  sutil que suele ignorarse y aqui esta bien resuelto.

  mascara 11x7), con aviso en consola si el grid es muy pequeno
  (tal como pide el PDF).
- Modo PERFECT=True: backtracker genera arbol perfecto (sin
  loops) + PerfectMode valida.
- Modo PERFECT=False (estilo Pac-Man): conectividad total, 4
  esquinas + centro abiertos, minimo 2 loops independientes,
  maximo 2 dead-ends reales.
- Reproducibilidad por seed (Random(options.seed)).
- Solucion mas corta con N/E/S/W via BFS (solver.py).
- Visualizacion ASCII + interacciones (regenerar, mostrar/ocultar
  camino, "cambiar color") funcionando en ui/cli.py.
- Clase unica reutilizable MazeGenerator en modulo standalone,
  API limpia (MazeOptions, MazeResult).
- LICENSE.md (MIT, permite reuso) cumple el requisito.
- Makefile (install/run/debug/clean/lint/lint-strict) coincide
  letra por letra con los flags exigidos por el subject.
- CI en GitHub Actions corre pytest + mypy --strict + flake8 en
  cada push/PR.
- scripts/maze_analyzer.py (provisto por el subject) presente.

Conclusion sobre el generador: nivel tecnico alto para este
proyecto. Maneja hasta el requisito mas fino (areas 3x3, loops
minimos, dead-ends, patron 42 opcional con warning).

--- CORRECCION: CONFIRMADA AL 100% ---

  alcanzables, 2 dead-ends reales (dentro de tolerancia) ->

- PERFECT=True (mismo grid): 0 loops, conectividad total ->

- Coherencia de paredes: OK en ambos casos.
- Reproducibilidad por seed: confirmada (misma seed -> archivo de

- Regeneracion en el menu interactivo (opcion 1): confirmada,

- Caso limite 2x2 (imposible en modo Pac-Man): falla con mensaje
  claro ("error: playable maze requires at least two loops"), sin
  traceback.
Conclusion: el generador y el solver de camino mas corto (BFS) son
correctos. NO se coincide con la afirmacion de que "el maze" sea

mas robusta y testeada del proyecto.

--- HALLAZGO: BUG DE RENDIMIENTO GRAVE EN EL MODO POR DEFECTO ---
Se midio el tiempo de generacion en PERFECT=False (modo por
defecto, el que usa config.txt) variando el tamano del grid:

  10x10 ->   0.48s
  20x20 ->   2.25s
  30x30 ->  10.42s
  40x40 ->  23.98s
  50x50 ->  TIMEOUT (>30s)
  80x80 ->  NO TERMINO en 3+ minutos (proceso matado manualmente)

Como contraste, PERFECT=True con 60x60 (3600 celdas) tarda ~1
segundo -> el problema esta aislado al post-procesado especifico
del modo Pac-Man (insercion de loops + reduccion de dead-ends),
no en la generacion base (recursive backtracker) ni en el patron
42.

Se usaron cProfile y mediciones de escalado para diagnosticar TRES
causas, todas en mazegen/modes/playable.py, y se corrigieron las
tres sin cambiar ningun comportamiento observable del laberinto
(304 tests siguen pasando, flake8 y mypy --strict siguen limpios):

1) _would_create_playable_open_3x3_area (para PlayableMode):
   Antes de rebarrer TODO el grid (todos los bloques 3x3 posibles)
   para decidir si UNA sola pared candidata crearia un area 3x3
   abierta. Costo O(ancho x alto) por cada candidato evaluado.
   FIX: se anadio _candidate_block_origins(), que calcula solo los
   (como mucho 4) bloques 3x3 que realmente podrian contener esa
   pared, en vez de barrer el grid entero. Costo O(1) por
   candidato.

2) _reduce_dead_ends: recalculaba find_dead_ends() (un barrido
   O(celdas) de TODAS las posiciones jugables) despues de abrir
   CADA pared individual, aunque abrir una pared solo puede
   afectar el estado de las 2 celdas que conecta.
   FIX: el set de dead-ends ahora se actualiza de forma
   incremental (dead_ends.discard(...) sobre las 2 celdas
   afectadas) en vez de recalcularse entero en cada iteracion.
   Justificacion de correccion: abrir una pared solo puede
   AUMENTAR el grado de las 2 celdas que conecta, nunca crear un
   nuevo dead-end en otra celda.

3) _dead_end_wall_candidates (bucle principal de
   _reduce_dead_ends): en cada iteracion del bucle reconstruia la
   lista de paredes candidatas iterando TODO el set de dead-ends
   restante, aunque solo se resuelve un dead-end por iteracion ->
   costo O(dead-ends^2) acumulado.
   FIX: se reemplazo por una cola barajada una sola vez
   (_shuffled_dead_end_queue) que se recorre con un cursor y solo
   se reconstruye cuando se agota Y hubo progreso desde la ultima
   reconstruccion (_open_safe_dead_end_wall). Pasa de
   reconstruir-todo-cada-vez a una sola pasada amortizada.

Verificacion tras los 3 fixes (mismos comandos, mismo hardware):

  10x10   ->  0.31s
  20x20   ->  1.38s
  30x30   ->  2.81s
  40x40   ->  2.29s
  50x50   ->  3.44s
  60x60   ->  6.02s
  80x80   ->  3.17s
  100x100 -> 23.69s
  150x150 -> 33.64s   (antes: no terminaba ni con los 2 primeros
                        fixes aplicados)

Mejora: un grid de 80x80 paso de "no termina en 3+ minutos" a
3.2 segundos. Un grid de 150x150 (22 500 celdas), que antes no
terminaba, ahora se genera en 34 segundos. Persiste cierta
variancia/crecimiento no lineal en tamanos muy grandes (100-150),
pero ya no es un bloqueo practico para el uso normal del proyecto
(demos, evaluacion, tamanos tipicos de 10-60).

Regresion: pytest (304/304), flake8 (0 errores) y mypy --strict
(0 errores) se re-ejecutaron despues de cada uno de los 3 fixes y
siguen en verde. No hay tests en el repo que usen grids mayores a
~25x25, por lo que este bug de rendimiento nunca habia sido
detectado por la suite existente -- recomendable anadir un test
de regresion de rendimiento (p.ej. generar un 60x60 con un limite
de tiempo) para evitar que vuelva a pasar desapercibido.
